五項核心指標（每個視口、每個方案）：

2. **主要讀值可達**：時間／x／y／速率那一列是否完整在視窗內（初始、開參數）。
3. **參數操作**：開參數後，發射速度滑桿與畫布是否**同屏**；改速度後畫布仍可見。

## 4. 三個有界方案
所有原型都是**覆蓋在真實頁面上的 CSS（B 另加一小段注入腳本）**，不是靜態 mockup，可實際操作：
```bash
npm run dev          # 另一終端
BASE_URL=http://localhost:3000 node docs/qa/2026-11-18-projectile-baseline/mobile-pack/try.mjs A 844x390   # base | A | B | C
```
（開有頭瀏覽器；右上角「⟲ rotate」可旋轉並保留狀態。重新整理會失去覆蓋。）

### 方案 A — 最小修補（只修橫向）
- **做什麼**：橫向短螢幕（`orientation:landscape` 且 `max-height:520px` 且 `min-width:661px`）改兩欄：左畫布滿高；右欄＝傳輸＋讀值（面板關）／參數面板（面板開，傳輸縮為畫布下方單列）。直向與桌機**不動**。
- **原型**：真實可操作（CSS 覆蓋）`prototypes/A.css`。
- **改動範圍估計**：1 檔（`app/projectile-c2.css`）新增約 **53 行 CSS**、0 行 TSX。（以上為我的低信心估計；**不是實際工時**。規劃量級：1–2 小時含審查。）
- **風險**：低。僅在橫向短螢幕生效；已量測 7 個非目標視口（1440×900、1366×768、1280×720、1024×768、768×1024、900×600、640×360）的 7 個關鍵元素位置與尺寸，與現況**完全相同**（`data/invariance.json`）。
- **合併實測**：把 A 併進真實樣式表後 production build，既有 Projectile E2E＋ThemeMenu 共 **88/88 通過**（含 axe 無違規）。
- **限制（誠實）**：橫向開參數時畫布 453×**172**（偏小）；發射速度與發射角兩條滑桿可見，發射高度及其餘需在面板內捲動；引導任務卡在橫向需捲動才見選項（畫布 154px）。
- **回退**：刪除該 CSS 區塊（單一 commit revert）。

### 方案 B — A ＋ 預設一鍵入口
- **做什麼**：A 的橫向修正，另在工具列（參數｜**預設**｜圖層｜放大視圖）加「預設」鈕：點一下開面板並展開既有「教學預設」清單，**3 次點擊 → 2 次**。
- **原型**：CSS（A＋工具列縮字）＋ `prototypes/B.js`（注入腳本，**只模擬互動**；步數是真的、程式是拋棄式）。
- **改動範圍估計**：A 的 53 行 CSS＋工具列字級 3 行＋ `ProjectileLab.tsx` 約 **30–50 行**（新增一顆按鈕與「開面板＋開預設選單」狀態）＋ E2E 1–2 條。規劃量級：3–4 小時含審查。
- **風險**：低–中。工具列由 3 鈕變 4 鈕：360px 已用縮字避免折行，**320px 較擠**；`預設` 鈕在**所有寬度**都會出現（桌機工具列也多一鈕，不是只有手機）——需 Owner 決定是否限手機。
- **已知問題（基準同樣存在）**：預設清單 10 項，最後一項（月球重力）會被底部固定工具列蓋住，需捲動。B 沒有解決這點。
- **回退**：revert 該 commit。

### 方案 C — 直向「App 殼層」（鎖視窗＋底部面板）
- **做什麼**：直向手機不再整頁捲動；畫布吃掉剩餘高度；參數面板成為最高 36dvh 的底部面板；面板開啟時傳輸列縮成單列。橫向＝A。
- **原型**：真實可操作（CSS 覆蓋）`prototypes/C.css`。**未適配、列為限制**：分享通知、圖層抽屜高度、放大視圖、長英文（C 僅驗證自由探索、引導預測前、圖層抽屜的截圖）。
- **量測結果**：面板關時畫布較大（360×800：**315px**；390×844：**359px**），**但面板開時反而更小**（208px／236px，base 為 235px 且仍 sticky）；**320×640 只有 155px→106px，劣於現況**。原因：標題＋模式列＋傳輸＋讀值＋底部工具列合計約佔 485px（800−315），不重做傳輸／讀值（dock）就拿不到更多畫布。
- **改動範圍估計**：目前 67 行 CSS 只是探針；要正式可用還需適配上述未處理狀態與 dock 重設計，約 **150–300 行**＋新 E2E。規劃量級：8–12 小時含審查（信心低）。
- **風險**：高。改變直向版型模型（整頁捲動→固定視窗），牽動引導、分享通知、放大視圖、400% zoom 重排（既有測試不涵蓋）。
- **合併實測**：併入後既有 Projectile E2E＋ThemeMenu 88/88 通過——**但這只代表既有測試沒偵測到，不代表直向殼層行為已驗證**。
- **回退**：revert；但若已依賴殼層改其他版型，回退成本上升。

### 已試且否決的做法（供 Owner 知情）
**直接恢復被覆蓋的畫布高度規則**：`app/projectile-c2.css` 先寫了 `height:clamp(235px,39vh,350px)`，約 30 行後又寫 `height:235px` 把它蓋掉（連 `scroll-margin-top:292px` 也是照那個高度寫的）。我試過恢復（畫布 312px@800），結果「完整讀值」摘要被頂到底部固定工具列下方，**axe `target-size`（serious）失敗**。在 800px 高的手機上首屏預算已用盡，所以直向畫布不能單靠這條規則變大。已從 A/B 移除。

## 6. 推薦（工程意見；**不是選型**）
1. **最低限度**：採 **A** — 唯一能修掉「橫向畫布被捲走」缺陷、風險最低、已用真實樣式表驗證 88/88。
2. 若 Owner 認為預設是高頻動作：**A＋B 的「預設」鈕**（把 R02 的 1–2 步要求補齊）；並決定桌機是否也顯示。
3. **不建議 C**：在不重設計傳輸／讀值區之前，畫布沒有淨增益（開面板時更小，320px 更差），而風險最高。若 Owner 仍想要殼層，建議先作為獨立的 dock 重設計任務，並先量化「直向畫布要多大才夠」。
4. 無論選哪個：直向畫布 235px 的問題**沒有被 A/B 解決**；需要另一個決定（見 §7 問題 3）。

## 7. 需要 Owner 裁決（OWNER REVIEW）
1. 橫向缺陷：**A**／**不處理**（接受橫向需捲動）／其他方向？
2. 預設入口：維持 3 步／**B 的「預設」鈕**（限手機？全寬？）／改成面板內晶片列（需新原型）？

4. 是否把「橫向」納入正式必驗視口（契約 R02 只列 4 個；目前橫向缺陷屬契約外）。
